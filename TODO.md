# To Do Later

Everything currently deferred or flagged as a known gap in `DEV_BUILD`, collected in one place so nothing gets lost. See `DEV_BUILD/SUPPORTED_HARDWARE.md` and `DEV_BUILD/PINOUT.md` for more detail on the hardware-specific items below.

## The big one

**Nothing generates an actual `direwolf.conf` yet.** The setup wizard (APRS settings, Radio setup, GPS setup) collects everything into `config.yaml` on Finish, but no backend currently turns it into a working Direwolf configuration. Every item below that says "collected but not applied" is downstream of this one gap — building the generator is what actually makes the rest of this list matter. (GPS is the one exception: `services/gpsconfig.py` applies gpsd/chrony/timezone directly from `config.yaml` on every boot, independent of Direwolf — see the GPS section below.)

## Digipeater / APRS

- Digipeat rules (alias/wide patterns) are collected via the wizard's Fill-in/Wide-area/Custom presets, but not yet applied anywhere.
- PHG (Power/Height/Gain) — now collected as three optional fields (Power/Height/Gain) on the RF Beacon subsection of the APRS step, matching Direwolf's `PBEACON` `POWER=`/`HEIGHT=`/`GAIN=` parameters. Not yet applied anywhere (per the big gap above); `DIR=`/directivity wasn't added, so Direwolf will treat it as omni.
- `AGWPORT`/`KISSPORT` — would let third-party APRS clients (Xastir, YAAC) use this station as a remote TNC. Flagged as low-priority/optional, not exposed.
- Digipeat `NOID`/preemptive options — couldn't confirm exact Direwolf syntax during research, not added.
- CSMA radio timing (`TXDELAY`, `TXTAIL`, `DWAIT`, `PERSIST`, `SLOTTIME`) — real, commonly-tuned settings, but about modem/PTT timing rather than APRS content. Belongs on the Radio step if it gets built at all.

## Map

- **Architecture changed entirely — the original raster tile-scraping design turned out to violate OSM's own tile usage policy, not just its etiquette.** `operations.osmfoundation.org/policies/tiles/` is explicit: "Offline use is not permitted on tile.openstreetmap.org", and bulk downloading is defined to include exactly what the old `services/tiles.py` did — pre-emptive fetching of tiles beyond what's actively being viewed, pre-seeding areas, building tile archives. All the earlier tuning (worker pools, concurrency, 429 backoff, cancel-in-flight fixes) was solving the wrong problem — no amount of "being more polite" makes a disallowed use case allowed. Caught by the user actually reading OSM's policy pages rather than trusting the "OSM tile usage policy asks bulk consumers to be considerate" framing this project had been using — that framing understated it.
- **Replacement: [Protomaps](https://protomaps.com/) / [PMTiles](https://github.com/protomaps/PMTiles)** — the legitimate, designed-for-this alternative (also what OSM's own policy page recommends for offline use: "vector tiles for offline use cases"). Instead of scraping individual tiles, `services/tiles.py`'s `RegionDownloader` shells out to the `pmtiles` CLI (`protomaps/go-pmtiles`, installed by `install.sh` as a static Linux binary — region-extraction is only implemented in the Go CLI, not the Python `pmtiles` package) to extract one region as a single `.pmtiles` file from Protomaps' hosted daily planet build, via HTTP range requests — only the bytes for the region are downloaded, not the whole planet. No API key or account needed for this self-hosted extraction path (distinct from Protomaps' unrelated commercial hosted-live-tiles product, which this project doesn't use).
- The wizard's *interactive* region-picker map is now **MapLibre GL JS + PMTiles**, not Leaflet + live OSM raster tiles — it renders from a coarse whole-world PMTiles layer (`world.pmtiles`, maxzoom 8, ~1GB) extracted once at install time by `scripts/precache_world.py` and served locally at `/map-data/world.pmtiles` (HTTP range requests, needs `starlette>=0.49.1` for both Range support and a real Range-parsing DoS fix — see `requirements.txt`). This means the picker itself — panning, dragging the pin, resizing the region rectangle via the four edge handles (now `maplibregl.Marker`s with custom DOM elements, GeoJSON source/layers for the rectangle instead of Leaflet's `L.rectangle`) — works with **or without internet at setup time**, unlike the old design which needed a live connection just to browse. Only downloading a more-detailed *region* on top of that coarse base still needs a real connection to Protomaps' build host: when offline, the wizard shows a note ("No internet found. The pre-cached map below will still work, but downloading a more detailed region needs an internet connection.") and disables dragging/clicking/the Download button, while leaving "Use station location" enabled (it only reads a locally-known position, no internet involved) and the map itself fully viewable. If `world.pmtiles` was never cached (no internet during install, or install.sh's best-effort fetch step was skipped), the step shows a distinct "map caching isn't available" message instead and nothing else renders.
- Basemap styling comes from `@protomaps/basemaps`' generated style JSON (vendored as `web/static/maplibre/style-light.json`/`style-dark.json`, picked at runtime via `prefers-color-scheme`), with fonts/sprites (`protomaps/basemaps-assets`) fetched by `install.sh` into `web/static/maplibre-assets/` at install time rather than committed to the repo — same "don't bloat the repo with third-party binary assets" pattern as `go-pmtiles` itself.
- No precise pre-download size estimate — a PMTiles extract's size depends on how much real map data exists in the area (dense city vs. open countryside at the same bbox/zoom can differ by an order of magnitude), unlike the old raster approach's clean geometric tile-count formula. The wizard says so honestly instead of showing a number, and shows real progress (bytes written to the output file so far, read straight off disk) once a download actually starts.
- The daily planet build lags real time by roughly a day and has no stable "latest" alias URL (confirmed live: today's date 404s, the previous one or two don't) — `find_source_url()` walks backward a few days checking each with a HEAD request rather than assuming any single date is ready.
- Not end-to-end tested — `pmtiles extract`'s exact CLI syntax was confirmed against Protomaps' own documented example commands and the Go source's function signature, and the binary itself was confirmed to download/extract correctly and run (`--help` on a compatible host), but the actual extraction subprocess, the world pre-cache step, and the whole MapLibre-based picker UI have not been run/tested end-to-end on real hardware/a real browser yet (needs a real Pi — this was developed on a Windows/MSYS sandbox that can't execute the Linux ARM64/x86_64 `pmtiles` binary at all, only its individual pieces verified via curl/Node/local Python tests).
- The Finish step's active-download warning and the progress display were both updated for the new `{active, done, cancelled, error, bytes, elapsed_s}` status shape (no more tile counts/percent — one CLI extraction isn't the thousands of individual per-tile requests the old design had).
- Still true either way: a running region download does not survive a reboot, and there's no way to resume it afterward — `Finish & Reboot` kills the whole process immediately, and once `config.yaml` exists, `first_boot` becomes permanently `false` and the wizard (the only UI that can start a download) is gone for good. The one-off whole-world precache only ever runs once, at install time, via `install.sh`.
- The main dashboard (`web/static/normal.html`, served once `first_boot` is false) now exists: a sidebar (station callsign/symbol/comment, digipeat/IGate mode badges, GPS fix, network connection, cached-map build dates + auto-update schedule, e-ink display model) next to a full-height MapLibre map centered on the station's home point (manual position, else a live GPS fix, else the center of the region picked during setup), reusing the exact same MapLibre GL JS + PMTiles + vendored style JSON as the wizard's region picker (prefers the downloaded region file over the coarse world one when both exist). Backed by three new read-only endpoints: `GET /api/config` (the saved `config.yaml`, with the password hash/salt stripped out), `GET /api/map/region-status`, and `GET /api/map/cache-info` (per-file build dates, from `services/tiles.py`'s `cached_build_date`).
- Still missing from that dashboard: live station markers/traces, heard-station history, and digipeat/IGate activity — there's no packet source to draw them from yet (downstream of the `direwolf.conf` generator gap above), so the map only ever shows the fixed home point, and the page says so honestly rather than implying more than it has. No settings can be *changed* from this page either (see "no post-setup settings UI" — still just the first-boot wizard for that).
- **Auto-update**: a checkbox + time-of-day field on the Startup wizard step, alongside the autostart/autorestart checkboxes — not Map caching or Finish (`config.yaml`'s `map.auto_update: {enabled, time}`) — defaulted **on** if there's internet reachable right when the Startup step renders, off otherwise (so a station that's normally offline doesn't end up with a background task quietly failing every day; a value already saved from a previous visit to the step, e.g. via Back/Next, always wins over re-deriving this default). The Finish step itself only shows reboot-related content (plus blocking Finish & Reboot on an in-progress region download — see below). Drives a systemd timer (`digipeater-tile-update.timer`/`.service`, installed unconditionally by `install.sh`) that runs `scripts/auto_tile_update.py` every 15 minutes. That script itself no-ops almost every run — it only does real work once the configured time has passed *and* it hasn't already run today (tracked via `map_data/.auto_update_last_run`) — at which point it checks Protomaps for a newer daily build than what's recorded in each file's `.build_date` sidecar (`services/tiles.py`: `cached_build_date`/`_build_date_marker_path`) and re-extracts the world map, plus the saved region if `map.north/south/east/west` exist in `config.yaml` (i.e. one was ever downloaded, in the wizard or by a previous auto-update run). A failed or offline attempt doesn't mark the day as done, so it just retries on the next 15-minute tick. Running every 15 minutes rather than pointing the timer at the exact configured time means changing that time in the UI later never needs any systemd unit to be touched/reloaded.
- Extraction now writes to a `.part` sibling file and only `os.replace()`s it onto the real output path once complete (both wizard-triggered and auto-update refreshes) — fixes a real race the old "delete-then-extract-in-place" approach had: anything reading `world.pmtiles`/`region.pmtiles` while a refresh was in progress could previously see a truncated/corrupt archive, and a failed refresh used to delete the old (still-good) file before finding out the new extraction wouldn't succeed. Also means `RegionDownloader.status()`'s live byte count now reads from the `.part` file while active, not the final path.
- Not end-to-end tested, same sandbox limitation as the rest of this section — the auto-update script's logic was verified by reading it closely and `python -m py_compile`, not by actually letting a systemd timer fire against a real Pi.

## User management

- Security mode + password now collected in the wizard (between E-Ink display and Startup) — three levels (`none`/`readonly`/`full`), simplified down from `ORIGINAL`'s four (`web.security.mode`: none/config/readonly/full). "Config password" (start/stop free, config locked) was deliberately dropped — not useful without a dashboard that actually distinguishes start/stop from config changes, and it's also what made `ORIGINAL`'s own gating inconsistent (see below). Password is hashed (PBKDF2-HMAC-SHA256, salted, `services/auth.py`) before it's written to `config.yaml` — improved over `ORIGINAL`, which stored it in plaintext and compared with a bare `==`.
- Not enforced anywhere — no login system/session/auth-gated endpoints exist in `DEV_BUILD` yet, so every mode currently behaves like "No security." This is the "Web UI security/password protection" item below, now half done (the setting exists; the enforcement doesn't).
- Worth knowing for whenever enforcement gets built: `ORIGINAL`'s "Read only" mode only gated Start/Stop/relay actions, not config-editing endpoints (`require_auth_if_readonly` vs `require_auth_if_config` were independent checks, and "readonly" wasn't included in the config gate) — so under `ORIGINAL`, "Read only" mode could still have its config changed with no password, despite the UI label ("view only without a password") implying otherwise. `DEV_BUILD`'s "Read only" should mean what it says: viewing open, any change (not just start/stop) needs the password.
